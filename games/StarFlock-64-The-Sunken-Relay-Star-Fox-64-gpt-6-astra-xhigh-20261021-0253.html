BEHIND THE FLOCK

StarFlock 64 is an original tribute to the exuberance of late-1990s rail shooters. All spacecraft, environments, characters, effects, music, and sound effects were created for this demo using code. No source-game assets are included. The title was chosen from 50 candidates using Python’s OS-backed random number generator.

ENGINE FEEDBACK

Liked most: Three.js geometry and scene composition make a coherent original low-poly art style practical without external assets.

Got stuck or guessed wrong: The r180 renderer installs a WebGL fallback by default; source inspection identified it and this build disables it explicitly. Full mission simulation exposed a Rapier collider-lifecycle crash. Stable body pools fixed it, and persistent narrow-phase overlap checks fixed a pickup reuse issue. Browser execution remains unverified.

Most important custom system: The encounter director, controller input layer, combat rules, lock-on targeting, mission states and 10-foot interface.

Hardest part: Coordinating fast projectiles, kinematic colliders, cinematic motion and UI feedback while keeping physics at a fixed timestep.

Remove or overhaul: Implicit backend fallback; a strict WebGPU mode should be a first-class constructor option.

One change: A built-in, public capability and device-loss reporting flow for player-facing applications.

PROMPT FEEDBACK · 404299fcd4

Liked most: The controller-first philosophy, explicitly looping attract mode, and single-file delivery define a clear arcade experience.

Confusing: “Native art style and assets” is ambiguous for Three.js, which supplies rendering primitives rather than a game’s art library. This demo uses original procedural assets informed by the source’s low-poly style.

Hardest: Delivering a complete, paced flight mission and polished interaction system without visual playtesting.

One test I would run: A complete PS5-controller sortie in a WebGPU browser, covering axis direction, every mechanic, both routes, pause/reconnect, and the carrier encounter.
