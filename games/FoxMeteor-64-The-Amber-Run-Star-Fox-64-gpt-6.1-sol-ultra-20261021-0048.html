Source Information

Date: 2026-10-21 08:24 UTC

Source: StarFox 64. FoxMeteor 64 is an original spiritual successor. Original procedural art, characters, music, mission and flight systems.

Tech: Three.js 0.180.0 (R180), WebGPU only with WebGL fallback disabled; @dimforge/rapier3d-compat 0.19.3; Web Audio API; Gamepad API; HTML/CSS/JavaScript. esbuild 0.25.12 bundles development modules into this HTML; runtime dependencies load from jsDelivr.

Art Direction: Faceted ochre canyon, turquoise river, monumental retrofuturist ruins, ivory and teal starfighters, warm celestial backdrop, cream and teal flight instruments.

Animation: Procedural transform animation; formation and attack AI; fixed-step flight and Rapier sensor/raycast collision simulation; particle bursts, engine pulses and authored mission timeline.

Testing: 2 browser smoke runs; 3 acceptance attempts (final 37/37 passed, including both routes, a normal resource-limited mission, boss phases, checkpoints, menu/settings flows, virtual PS5-standard inputs, attract mode and unsupported/touch device flows); 3 focused regression attempts (final 13/13 passed: real Rapier sensor collisions, roll/pitch, difficulty, shield phases, controller disconnect, reset/resource lifecycle and Web Audio); 2 UI runs (30/30 each); final input/fixed-step integration 11/11 passed (total integration-run count unknown); 9/9 final packaged-file checks in one run; syntax checks and visual screenshot inspection. Review/testing corrected 13 game integration/lifecycle issues, 0 confirmed critical/unplayable game issues. Headless capture configuration and test fixture/timing/import issues were also corrected. Physical PS5-controller/TV testing: unknown.

Engine Feedback

Liked most: Three.js makes the procedural world, aircraft and readable combat effects easy to compose. Rapier supplies reliable sensors and ray queries without tying the art to the physics.

Stuck or guessed wrong: The renderer automatically supplies a WebGL fallback, so strict WebGPU required an adapter check and disabling that callback. Input edges initially repeated across physics substeps. Linux headless screenshots were blank despite working GPU draws; headed Chrome under Xvfb presented the same WebGPU scene correctly.

Most important system built: The complete flight-game layer: authored mission beats, enemy formations, lock-on weapons, route choice, wing rescue, boss states, checkpoints, attract autopilot and controller menus.

Hardest part: Coordinating fixed-step Rapier collisions, held and edge-triggered inputs, camera framing and readable targets in a moving rail-shooter world.

Remove or overhaul: Replace implicit renderer backend fallback with an explicit backend policy at construction.

One change: A documented strict WebGPU initialization option with one clear capability error would simplify WebGPU-only delivery.
