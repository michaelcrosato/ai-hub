Source information

Star Skipper. An original spiritual successor to StarFox 64. No source-game assets are used. The ships, characters, environment, music, and effects are original procedural work. This is an independent fan-inspired project, not an official Nintendo product.

Date. 2026-10-21 11:11 UTC

Tech. Three.js 0.180.0 (R180), strict WebGPU / WebGPURenderer with WebGL fallback disabled, @dimforge/rapier3d-compat 0.19.3, Web Audio API, Gamepad API, HTML5, CSS3, JavaScript ES modules. Barlow Condensed and Space Grotesk via Google Fonts.

Art direction. Original procedural low-poly space opera: faceted coral islands, teal sea, ivory interceptors, monumental coastal machinery, a ringed planet, and amber/cyan effects. All game meshes, portraits, and effects are created in code.

Animation. Procedural transform animation, spring-smoothed chase cameras, banking and barrel rolls, homing projectiles, particle bursts, and Rapier rigid-body debris. Flight and combat use a fixed 60 Hz physics step; authored mission events drive transitions and dialogue.

Testing. Text-only Playwright browser checks for boot, keyboard/gamepad mapping, axis inversion, pause, touch-only input gating, and attract mode. Seven browser executions: one initial boot check; two runs stopped by headless GPU device loss; one interrupted after exposing slow mission-clock catch-up; one successful full check covering two complete attract missions, both routes, both boss victories, looping, and input exit; and two final boot/control smoke checks (the first used a premature fixed-delay brake assertion; the second waits for the actual input state). Six JavaScript syntax checks passed. Five distinct test findings were corrected: missing favicon, missed quick keyboard taps, unsuitable headless GPU configuration, overly restrictive frame-time catch-up, and a premature fixed-delay input assertion in the test harness. One finding was critical in the test environment (GPU device loss). No screenshots, visual review, physical-controller testing, or performance/balance tests were performed. Test execution cost is unknown.

Environment. Codex CLI; Ubuntu 26.04.1 LTS on WSL2, Linux 6.18.33.2-microsoft-standard-WSL2. Successful browser validation: Google Chrome for Testing 153.0.8010.12, headless WebGPU via Vulkan/SwiftShader. Initial attempts used Google Chrome 154.0.8037.57.

Model. OpenAI; requested model gpt-6-astra; reasoning effort high; runner codex. Actual serving model is unknown beyond the supplied execution identity.

Usage. Usage: Session time 33m 36s; tokens 2,983,408 total (2,916,238 input including 2,817,536 cached and 0 cache-write; 67,170 output including 22,479 reasoning); API cost $7.163056 USD (Estimated standard API token cost; not subscription billing).

Engine feedback

Liked most. The scene graph and reusable procedural geometry made it easy to give the ships, landscape, and encounters one coherent style.

Stuck or guessed wrong. The initial headless browser GPU flags caused device loss. Chrome for Testing with an explicit Vulkan/SwiftShader WebGPU adapter worked. Three.js also required explicitly disabling its default WebGL fallback.

Most important custom system. The shared flight/combat simulation: corridor and all-range steering, buffered input, charged targeting, squad support, checkpoints, mission scripting, and the attract pilot.

Hardest engine work. Keeping fixed-step Rapier collisions, projectile sweeps, camera motion, and WebGPU scene state synchronized across encounter transitions and long frames.

Remove or overhaul. Implicit renderer backend fallback; a strict WebGPU requirement should be expressible directly in the public constructor.

One change. More actionable device-loss diagnostics that distinguish application errors from headless-driver configuration problems.

Prompt feedback

Prompt version. 404299fcd4

Liked most. The precise stack, single-file deliverable, controller-first UX, and attract-mode requirements gave the demo a clear purpose.

Confusing. The initial request for usage estimates was superseded by the final instruction not to estimate usage. The runner-owned usage marker is used instead.

Hardest part. Delivering a complete, readable mission with branching objectives, all-range flight, and a boss while doing no visual review.

One test I would run. A complete couch-distance sortie on a physical DualSense controller to assess stick feel, combat readability, and menu focus. This was not performed.
